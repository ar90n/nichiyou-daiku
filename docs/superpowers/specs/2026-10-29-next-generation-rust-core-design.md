# 次世代（Rust 版）と R1 core 設計

- 日付: 2026-10-29
- ステータス: 設計（未実装）
- ブランチ: `next`（次世代を育てる長寿命のブランチ）

## 背景

ファイルワゴンを設計している途中で、ユーザーが「TS に移植すればアプリになる」と考えた。core（DSL・配置・留め具・
検証）は build123d に頼っておらず、build123d を使うのは絵（確認用の画像・図面・部品図・組み立て手順）と 3D の
書き出し（STL・STEP）だけだと確かめた（2026-10-25）。やりたいことは「.nd を取ってきてクライアント側で表示する」
こと。TS と Rust（WASM）を比べ、ユーザーは「build123d を使わないなら Python でやる意味はない」として Rust を選んだ。

## 次世代の決定と理由

1. **全部 Rust に置き換える**（ユーザー）。core、CLI、レポート、絵、プラグインまで Rust にし、移し終えたら
   Python 版を消す。実装が最後に 1 つになり、DSL の意味が 2 か所でずれる心配がなくなる。
2. **build123d で作っている出力は全部残す**（ユーザー）。形は「箱と、面に垂直な円柱の穴」だけなので、確認用の
   画像・図面・部品図・組み立て手順は自前の隠れ線処理で作る。STL は自前で書く。STEP は Rust の CAD カーネル
   （truck など、WASM でも動くもの）で出す。どれを使うかは R5 で決める。
3. **アプリの最初の版は、表示と問題の一覧**（ユーザー）。.nd を URL かファイルから開き、3D で回して見る。
   部材名のラベルと、validate の問題（ビスのぶつかりなど）も出す。編集はしない。
4. **同じリポジトリの、別のブランチ `next` で、次世代として育てる**（ユーザー）。例の .nd、DSL 仕様、プラグイン、
   評価の仕組みをそのまま使え、Python 版との比較も同じ場所でできる。
   - main は今の Python 版（第 1 世代）のまま手入れを続ける。
   - R1〜R6 は `next` から作業ブランチを切って作り、レビューと CI を通してから `next` に入れる。
   - `next` の中の Python 版は、正解ファイルを作るために R6 まで残す。その間に main で Python 版の動きを
     変えたら、`next` に取り込んで正解ファイルを作り直す。R6 で Python を消したあとは、main の変更は手で移す。
   - `next` が R6 まで終わり、入れ替えてよいとユーザーが判断したら、`next` を main に入れて第 2 世代にする。
   - `make check` と CI に Rust を足すのは `next` だけ。main の CI は変えない。
5. **順番は core と表示が先、絵は後**（ユーザー承認）。1 つずつ仕様 → 計画 → 実装の順で進める。
   1. R1 core: DSL、接続の検証、未知数の解決、配置、留め具・下穴・座掘り、ぶつかり判定。`validate --json`
      と同じ JSON を出し、Python 版と一致させる（この文書の後半）。
   2. R2 ブラウザ: WASM と three.js。.nd を開いて 3D 表示、部材名のラベル、問題の一覧。静的なサイトとして置ける形。
   3. R3 組み立てマニュアル（2026-10-31 に入れ替え、ユーザー承認。R2 を確かめたあと、ビューアーで組み立て
      マニュアルを見たいという要望から。CLI より先にする）: A 手順送り（部品表と、手順を送って 3D で見る。
      手順の計画を含む）→ B 寸法（新しい部材の位置の寸法線）→ C 紙のマニュアル（自前の隠れ線処理で部品図と
      手順の図、印刷。元の R4 の図面の描き方を取り込む）。A は `2026-10-31-r3a-assembly-steps-design.md`、B は `2026-10-31-r3b-step-dimensions-design.md`。C は C1 部品図 → C2 手順の図 → C3 マニュアルと印刷に分ける（2026-11-01、ユーザー承認。C1 は `2026-11-01-r3c1-part-drawings-design.md`、C2 は `2026-11-01-r3c2-step-drawings-design.md`、C3 は `2026-11-01-r3c3-manual-design.md`）。
   4. R4 CLI: `validate` と `report`（材料表・買い物リスト・木取り・ビス・ドリル）、R3 の描き方を使う
      `render`・`drawing`・`steps`。プラグインの `bin/nichiyou-daiku` を Rust 版に替える（配り方はビルド済みの
      バイナリ）。R4a 文字（CLI の骨組み・`validate`・`report`）→ R4b 絵（`render`・`steps`・`drawing`・`view`）→ R4c 配る に分ける（2026-11-01、ユーザー承認。R4a は `2026-11-01-r4a-cli-text-design.md`）。R4b は R4b1（PNG の土台・`render`・`steps`、`2026-11-02-r4b1-render-and-steps-design.md`）→ R4b2（`drawing` の PDF）に分け、`view` は R4c でブラウザのビューアーを開く形にする（2026-11-02、ユーザー承認）。R4a の後に、皿取りと部品図の題名の見せ方を小さな仕様で入れる（ユーザー。`2026-11-02-countersinks-and-part-titles-design.md`）。
   5. R5 3D の書き出し: STL と STEP。
   6. R6 片付け: Python 版を消し、評価・ドキュメント・CLAUDE.md を Rust 版に合わせる。
6. **評価の仕組み（`evals/design`）は Python のまま残す**（前提、ユーザー了承）。製品ではなく開発の道具なので、
   使う CLI だけを Rust 版に替える。

## R1 core の決定と理由

### 1. 一致の確かめ方: Python 版の出力を正解ファイルにして比べる（ユーザー）

同じ .nd を Python 版にかけた結果を正解ファイルとしてリポジトリに入れ、Rust 版の結果と比べる。テストのたびに
Python 版を動かす方法は CI に Python が要り、Python を消すと使えなくなる。Python のテスト（14,700 行）を書き直す
方法は重すぎる。正解ファイルなら、Python を消したあとも退行テストとしてそのまま残る。

### 2. パーサーは自前で書く（ユーザー）

文法は 87 行と小さい一方で、`FL<0` と変数名、`S(Slim:3.8x65)` のように前後で読み方が変わる字句がある。Lark は
文脈で字句を読み分け、構文エラーでは「その位置で受け付ける字句」を数えて `Expected one of: …` を作っている。
自前の字句解析とパーサーなら、この読み分けと受け付ける字句の数え方を正確に再現でき、依存も増えない。lalrpop は
文法を写しやすいが文脈に応じた字句解析は結局自前になり、chumsky は受け付ける字句の数え方が Lark と違う。

### 3. 組み立て

- リポジトリの直下に Cargo のワークスペース（`Cargo.toml`）を置き、部品は `crates/` の下に並べる。Python の
  `src/` と並べて置き、R6 で `src/` を消す。
- R1 で作るのは `crates/nichiyou-daiku-core` だけ。中は Python の構成にそろえる。
  - `piece`: 材種と断面の表（今と同じく、この表を唯一の元にする）
  - `geometry`: 面、辺、オフセット、箱、面上の点
  - `anchor`・`connection`: 接続の種類とダボ・ビスのプリセット、接続の検証
  - `model`: 部材・接続・手順のブロック（手順の計画は R3）
  - `dsl`: 字句解析、パーサー、変数と式の評価、エラー
  - `resolve`: 未知数（`=?`、`?`）を解く
  - `placement`: 配置ソルバー、矛盾、グループ、重なり
  - `assembly`: 留め具、下穴・座掘り、穴のぶつかり
  - `diagnostics`: 問題の一覧と `validate --json` の JSON を組み立てる（問題の文面もここで作る）
- R1 の出口はライブラリの関数 2 つ。.nd の文字列から `validate --json` と同じ JSON を返す関数と、穴の一覧
  （下の「穴の一覧の形」）を返す関数。穴の一覧は R2 のビューアも使う。CLI（R4）と WASM の包み（R2）は作らない。
- 依存は serde と serde_json だけ。core はファイルもスレッドも使わず、`wasm32-unknown-unknown` でビルドできる
  状態を保つ（R1 の CI でも確かめる）。R2 で包むときに困らないようにするため。

### 4. 処理の流れとエラー

- 流れは Python 版と同じ: 文字列 → 字句解析（位置付きの字句、文脈で読み分ける）→ 構文解析（位置付きの木）→ 評価
  （変数・式・プリセット・`?`）→ モデル（接続の検証）→ 未知数の解決 → 配置 → 留め具・穴・ぶつかり・重なり →
  問題の一覧 → JSON。
- エラーの型は 1 つ。種類（`file`・`syntax`・`semantic`・`validation`・`assembly`・`unexpected`）、文面、行、列を
  持ち、`validate --json` の `error` 欄にそのまま対応する。途中で止まるもの（構文・意味・値の誤り）と、最後まで
  調べて並べる問題（矛盾・つながっていない・留め具・穴のぶつかり・重なり）の分け方も Python 版と同じ。
- 文面は Python 版の文字列をそのまま写す。エージェントは文面を頼りに直すので、仕様の一部として扱う。位置も
  Python 版と同じく、いちばん内側の文かアンカーを指す。
- 数値は f64。丸め（`round_mm`）と JSON での数の書き方（`400.0`、`129.666667`）も Python 版に合わせる。
- 利用者の入力が原因ならパニックせず、必ずエラーとして返す。パニックはバグなので `unexpected` として報告する。
- 式の入れ子（括弧とマイナス）は 100 重まで。それより深いと再帰でスタックがあふれ、プロセスごと落ちる（ブラウザでは
  1 MB のスタックで先にあふれる）ので、位置付きの構文エラーにする。Python 版は括弧を 1 万重でも読むが、実際の .nd
  では起きない。足し算・掛け算の長い並びは入れ子にしないので、何個並んでも読める（最終レビュー、2026-10-30）。

### 5. 穴の一覧の形

R1 で新しく決める JSON。Python 版にはないので、正解ファイルを作るスクリプトが Python 版の `Assembly` から作る。
.nd が構文・意味・値の誤りで止まるときは作らない。

```json
{
  "pieces": {
    "leg_fl": [
      {"face": "right", "center": [89.0, 19.0, 527.75], "diameter": 2.5, "depth": null},
      {"face": "left", "center": [0.0, 19.0, 527.75], "diameter": 10.0, "depth": 51.0}
    ]
  },
  "fasteners": [
    {"base": "apron_upper_left", "target": "leg_fl", "kind": "screw", "diameter": 3.8, "count": 2}
  ]
}
```

- `pieces`: 部材ごとの穴（下穴・ダボ穴・座掘り）。`center` は穴が入る面の上の中心を、部材の座標（x が幅、y が
  厚さ、z が長さ、原点は部材の最小の角）で表す。`depth` が null なら貫通。並びは `face`、`center` の順で決める。
- `fasteners`: 接続ごとの留め具の種類・径・本数を、接続を書いた順に。

### 6. テスト

- 正解ファイルは `crates/nichiyou-daiku-core/tests/corpus/` に、名前ごとに `名前.nd`、`名前.validate.json`、
  `名前.holes.json`（作れるときだけ）を置く。
- 元にする .nd:
  - 例（`examples/nd_files/`）: 6 件
  - DSL 仕様と作例（`patterns.md`）の中の例: 15 件
  - 評価で作られた設計（`evals/design/runs/`、git の外）: 重複を除いて 383 件
  - Python のテストで `parse_dsl` に渡す文字列: `DSLParser.parse` を包む pytest プラグインでテストを走らせながら
    書き出し、重複を除いたもの（エラーになる入力も多く含む）
- 正解ファイルは Python のスクリプト `tools/make_goldens.py` で作り、コミットする。作り直すのは .nd を足したときと、
  R6 までに Python 版の動きを変えたとき。R6 で Python を消したあとは Rust 版が正解になり、動きを変えるときは
  正解ファイルの差分をレビューして更新する。
- 完全な互換性は求めない（ユーザー、2026-10-30）。Python 版より良くなる違い（より正確、より分かりやすい）は
  認める。悪くなる違いは認めない。
- 比べ方:
  - 数値は 1e-6 以内、文字列は完全一致。
  - 意味や値のエラーは文面まで一致させる。
  - 構文エラーは種類・行・列を一致させる。文面は「見つけた字句」（`Unexpected token '…'` など）、「受け付ける
    字句の一覧」（`Expected one of: …`）、「後ろの案内」（`'?' (unknown) works in compact notation only …` など）に
    分け、見つけた字句と後ろの案内は完全一致で比べる。
  - 受け付ける字句の一覧は、Rust 版が Python 版の一覧を全部含めばよい（ユーザー、2026-10-30）。Lark は LALR の
    都合で、詰まった字句によっては誤りに気づく前に式を途中まで畳み、その場所で本当に続けられる字句（`*`、`/`
    など）を一覧から落とす（`(a:2x4 =100` の終わりでは `')', '+', '-'`、`(a:2x4 =100 ]-` では `')', '*', '+',
    '-', '/'`）。自前のパーサーは、その場所で続けられる字句を全部出す。
  - それ以外で合わないものは、良くなる違いなら `tests/corpus/known_differences.toml` に名前と理由を書いて残す。
- 全件の比較を 1 つのテストで流し、何件合ったかを出す。正解ファイルとの比較が、最初に落ちるテストになる（TDD）。
  パーサーやソルバーの細かいところには Rust の単体テストも足す。
- `make check` に `cargo fmt --check`・`cargo clippy -- -D warnings`・`cargo test`・`wasm32-unknown-unknown` での
  ビルドを足し、Dagger の CI にも Rust を入れる（`next` だけ）。

### 7. R1 で作らないもの

CLI（R4）、WASM の包みとビューア（R2）、レポート（R4）、手順の計画と絵（R3）、STL・STEP（R5）。

### 8. R1 が終わる条件

- 集めた全件で、Rust 版の `validate --json` 相当と穴の一覧が、上の比べ方で正解ファイルと一致する（既知の違いを除く）。
- `cargo fmt --check`・`cargo clippy -- -D warnings`・`cargo test`・`wasm32-unknown-unknown` でのビルドが通る。
- `next` で `make check` と `make ci-local` が通る。
