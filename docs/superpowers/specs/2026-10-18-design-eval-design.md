# 設計スキルの評価（M5-1）設計

- 日付: 2026-10-18
- ステータス: 設計済み（ユーザーの確認待ち）
- 対象: M5-1（M5 エージェントの設計ループ。順番は 1 測れるようにする → 2 設計の質を上げる → 3 実際に家具を設計して
  使い倒す。ユーザー決定）

## 背景

設計スキル（`skills/design/`）は M3 でプラグインにした。効き目は M3 のとき `/tmp` の使い捨ての仕組みで一度だけ測った
（非対話の sonnet に依頼 3 件 × 2 回。スキルを使ったか、validate が通ったか、外形が合ったか、画像を見たか）。
リポジトリには残っておらず、スキルや CLI を変えても設計の質が落ちていないかを確かめる手段がない。2 で質を上げるにも、
まず同じ物差しで何度でも測れる必要がある。

設計の手順は、もともと Web サービスでも使えるよう「プロンプト」として書いていた（ユーザー）。今回は扉を開けておくだけで、
Web サービスの形は測らない。

## 目的

スキルや CLI を変えたとき、同じ依頼セットで Claude Code にスキルを使って家具を設計させ、設計の質を自動で採点し、前と
比べられる。頻度と規模を選んで、使用量を調整できる。

## 決定と理由

1. **測るのは Claude Code でスキルを使ったときの設計**（ユーザー）。Web サービスとして公開するための検証ではない。
   手順と規則（SKILL.md・patterns.md）は道具に依存しない書き方に保ち、あとで Web サービスのシステムプロンプトに
   流用できる扉を開けておく。
2. **採点は機械・LLM・人をすべて組み合わせる**（ユーザー）。機械と LLM は自動で、人はレポートの画像で気になる回だけ見る。
3. **規模は 2 段**（ユーザー）。普段は ★ の 5 件 × 1 回（`make eval`）、節目に 10 件 × 3 回（`make eval-full`）。
   件数・回数・モデルは指定でき、回す頻度で使用量を調整する。
4. **設計も採点も `claude -p` で回す**（ユーザー承認）。API キーがなく、`claude -p` ならふだんのログインのまま回せ、
   構造化出力（`--json-schema`）とプラグインの読み込み（`--plugin-dir`）がある。使うのはふだんの Claude Code と同じ
   使用量の枠で、測るほど開発に使える分が減る（ユーザー了承。量は試運転を見て決める）。`--bare` は API キーが必須なので
   使わない。
5. **依頼セットは 10 件**（ユーザー承認。§1）。1・2 はスキルの例とほぼ同じで、設計する力より易しい道筋が壊れていないかを
   見る。実際に作りたい家具の依頼が出てきたら差し替える。
6. **設計させるモデルは sonnet、採点するモデルは opus**（ユーザー）。sonnet は枠の消費が少なく、利用者が使う標準的な
   モデル。採点を測る対象と同じモデルにすると、自分の出力に甘くなりやすい。節目には設計を opus でも回せる。
7. **機械の項目は別々の列に出し、見出しの数字は「機械の項目が全部合格した回の割合」**。一つにまとめると、どこで
   落ちたか分からない。LLM の項目も別々に出す（§3・§4）。
8. **1 回ごとに環境を切り離す**。空の作業ディレクトリで動かし、ユーザーの MCP・設定・CLAUDE.md は読ませない。CLI は
   リポジトリの今のコードを使う（`~/.local/bin` の古い CLI を使うと、今のスキルと食い違う）。前の回の残りやユーザーの
   環境が結果に混ざると、何を測っているか分からなくなる。
9. **時間切れや仕組みのエラーは「設計の失敗」と分けて記録し、止まっても続きから回せる**。混ぜると、仕組みの不調が
   設計の質の低下に見える。1 回 5〜30 分かかるので、止まるたびに最初からでは回せない。
10. **レポートは Markdown（`report.md`）に画像を並べる**。チャットにそのまま出せる（ユーザーの希望）。claude-api
    スキルの HTML ビューアは、入っている版では画像を出せない。
11. **置き場所は `evals/design/`**。リポジトリはドットファイル（`.claude/` など）を入れない決まりなので、claude-api
    スキルが勧める `.claude/hillclimb/` は使わない。結果（`runs/`）は git に入れない。

## スコープ外

- 設計の質を上げる変更（M5-2）、実際の家具での使い倒し（M5-3）
- Web サービスの形（API でツールを渡して回す）の評価
- 依頼の自動生成、CI での自動実行（使用量の枠を使うため、手で回す）

## 設計

### 1. 依頼ファイル

`evals/design/cases/<名前>.toml`。依頼文、★（普段の回し方に入れるか）、要件。依頼文の最後には、どれも「質問はせず、
決まっていないところは既定値で進めて。ファイルはカレントディレクトリに書いて。」（英語の依頼は同じ意味の英文）を付ける。

```toml
request = "2x2材で花台を作りたい。幅400×奥行300×高さ700mm。天板は1x4、床から200mmの位置に棚を1段。…"
core = true
tags = ["例にない材"]

[size]            # 幅（x）×奥行（y）×高さ（z）
width = 400
depth = 300
height = 700
tolerance = 1

[lumber]
allowed = ["2x2", "1x4"]
required = ["2x2", "1x4"]

[legs]
count = 4

[[shelves]]       # 水平の部材の上面か下面が、床からこの高さ
at = 200
tolerance = 5
```

段の数を見る依頼（本棚など）は `[levels]`（`count = 4`、`equal = true`）を書く。

### 2. 回し方

```bash
make eval                 # ★ の 5 件 × 1 回、設計 sonnet・採点 opus
make eval-full            # 10 件 × 3 回
uv run python -m evals.design.run --cases plant-stand,desk --reps 2 --model opus
uv run python -m evals.design.run --resume runs/<日時>   # 止まった回の続き
```

- 1 回（依頼, 何回目）ごとに `runs/<日時>/<名前>-<回>/` を作業ディレクトリにして `claude -p` を動かす:
  `--plugin-dir <リポジトリ>`、`--model`、`--output-format stream-json`、`--strict-mcp-config`（MCP なし）、
  `--setting-sources` でユーザーの設定を読まない、`--no-session-persistence`。使える道具はファイルの読み書き・検索・
  `Skill`・Bash。Bash は作業ディレクトリの外に届くもの（`rm`・`git`・`curl`・`wget`・`ssh`・`sudo`・`uv tool`・`pip`）と
  Web の取得・検索だけ断る。M3 の評価でエージェントは `sed`・`cat`・`python3` も使っていて、断ると人の使い方と違う動きに
  なる（計画のとき）。断られた呼び出しは数を記録する。
- Claude Code は作業ディレクトリごとに `~/.claude/projects/<パス>` を作る（自動メモリの空のディレクトリ）。1 回ごとに
  作業ディレクトリが違うので、ファイルが 1 つもなければ回し終えたあとに消す。
- `PATH` の先頭にリポジトリの `.venv/bin` を置き、プラグインの `bin/nichiyou-daiku` が今のコードの CLI を使うようにする。
- 作業ディレクトリはリポジトリの外（一時ディレクトリ）に作り、回し終えたら `runs/<日時>/<名前>-<回>/` に写す。プラグインは
  リポジトリから `evals/`・`.claude/`・`CLAUDE.md` を除いた写し（git が管理する・管理しうるファイル）から読む。
  リポジトリの中で動かすと、Claude Code は git のルートをプロジェクトとみなして開発者の CLAUDE.md・設定・自動メモリを
  読み（実装のときの試運転で `memory_paths` が開発者のメモリを指していた）、プラグインのルートから採点の要件や前の回の
  設計も読める（実装のとき、DeepSeek のレビューで指摘）。採点（`--self-check` も）も同じくリポジトリの外で動かす。
- 同時に回すのは 2 回まで（指定できる）。1 回の上限は 40 分で、超えたら打ち切って「時間切れ」とする。
- 結果は 1 回終わるごとに書く。`--resume` で終わった（依頼, 回）は飛ばす。続きは最初の回の条件（依頼・回数・モデル。
  `meta.json`）で回し、別の条件を付けたら断る（実装のとき。条件が混ざった結果を防ぐ）。
- 切り離しは確かめた（2026-10-18、haiku で 1 往復）。`--setting-sources project --strict-mcp-config` で、MCP は 0、
  プラグインはこのリポジトリのもの（と Claude Code 組み込みのもの）だけ、ユーザーのスキル（`~/.claude/skills`）は
  読まれず、`memory_paths` は作業ディレクトリの空の自動メモリだけだった。試運転でも `init` の記録で同じことを確かめる。
- 標準入力は `/dev/null` にする（`claude -p` が標準入力を 3 秒待つ）。
- Claude Code には組み込みの `design` スキルがあり、このプラグインの `nichiyou-daiku:design` と名前が重なる。
  「スキルを読んだか」は `Skill` の呼び出しの名前が `nichiyou-daiku:design` かで数える（M3 の評価は名前に design を
  含むかで数えていたので、取り違えを数えていた可能性がある）。名前の重なりそのものは M5-2 で扱う。

### 3. 機械の採点

作業ディレクトリの `.nd`（依頼の名前と同じ名前があればそれ、なければ 1 つだけあるもの）を nichiyou-daiku で読んで
確かめる。`.nd` がない、2 つ以上あって選べないときは「ファイルなし」で全項目不合格。

| 項目 | 合格の条件 |
|---|---|
| valid | `validate --json` の `valid` |
| size | 外形の 3 辺が要件と許容差内で合う（向きは問わない） |
| orientation | 幅が x、奥行が y、高さが z。脚のない箱もの（本棚）は幅と奥行の向きを問わない: 最初の部材の側板の幅（奥行）が必ず x になる（実装のとき、最終レビューで指摘） |
| lumber | 使った材種が `allowed` に収まり、`required` をすべて使う |
| legs | 長さの方向が縦で、下端が床（z=0）にある部材の数が要件どおり |
| shelves | 長さの方向が水平の部材の上面か下面が、要件の高さに許容差内である |
| levels | 厚みの方向が縦の板を、上面の高さ（5mm 以内は同じ段）でまとめた段の数が要件どおり。等間隔の要件は、段の間隔の最大と最小の差が 5mm 以内。「一番上の段が板」は、一番上の段の上面が外形の高さ |
| fasteners | 要件のダボ・ビスが接続に使われている |
| steps | 部材が 6 本以上なら steps ブロックがある |

要件にない項目は「対象外」とし、合格率の分母に入れない。見出しの数字は、対象の項目が全部合格した回の割合。

### 4. LLM の採点

仕組みのほうで最後の `.nd` を `nichiyou-daiku render` し、その画像と依頼文を採点用の `claude -p`（`--model opus`、
道具は `Read` だけ、`--json-schema`）に渡す。項目ごとに `{pass, reason}` を返す。

1. 依頼された家具に見える（天板・座面・棚・脚など、主な部分がそろっている）
2. 宙に浮いた部材や、ほかの部材を突き抜けた部材がない（どの部材も床かほかの部材に支えられている）
3. 部材の向きが自然（脚は縦、天板・棚板・座面は水平）

入れなかった項目: 脚や棚の数（機械で確かめるので二重に数えない）、使いやすさや丈夫さ（基準があいまいで採点がぶれる）。
依頼文と画像は採点される側のデータとして渡し、そこに書かれた指示には従わないよう採点の指示に書く。

`--self-check` は、採点の正しさを本番の前に確かめる。わざと壊した設計（天板がない、横倒しで脚が寝ている）は不合格に、
スキルの例は合格にすること。

### 5. 記録

`runs/<日時>/` に:

- `results.jsonl`: 1 回 1 行。依頼の名前、何回目、設計したモデル（応答から取る）、機械と LLM の項目ごとの合否と理由、
  時間（`duration_ms`）、ターン数（`num_turns`）、使用量（`total_cost_usd` と `usage`）、スキルを読んだか、
  validate・render の回数、画像を見たか、断られた道具の呼び出し（`permission_denials`）、採点のモデルと使用量。
  いずれも `claude -p` の最後の `result` の記録にある（2026-10-18 に確かめた）。
- `errors.jsonl`: 時間切れ・仕組みのエラー（`claude` が異常終了、採点の失敗など）。種類と使用量。`results.jsonl` には
  入れない（入れると続きから回すときに飛ばされ、仕組みの不調が設計の失敗に数えられる）。
- 回ごとのディレクトリ: エージェントが書いたファイル、`run.jsonl`（会話の記録）、`render.png`、採点の入出力。

### 6. レポート

`runs/<日時>/report.md`（英語。プロジェクトのほかの出力と同じ。チャットで見せるときに日本語で説明する）:

- 回した条件（依頼の件数、回数、モデル、日時、リポジトリのコミット）
- 項目ごとの合格率と 95% の幅、時間・使用量の中央値と幅（絶対値で）
- 依頼ごとの表と、回ごとの画像・LLM の判定理由
- `--compare <前の結果>` のときは、項目ごとの増減を並べる
- 失敗した試行は残し、続きから回してあとで採点できたものにはその旨を書く。見出しに、まだ採点できていない数を出す

### 7. 試運転（計画のとき、2026-10-18）

- `--self-check`: 例は 3 項目とも合格、天板のない設計は「家具に見える」が不合格、横倒しの設計は「向き」が不合格（理由も
  見たとおり）。1 回 5〜9 秒、使用量は 0.08〜0.17 USD 相当。
- `plant-stand` を sonnet で 1 回: 機械と LLM の項目がすべて合格。13.6 分、27 ターン、使用量は設計 1.63 USD 相当・
  採点 0.1 USD 相当。スキルを正式な名前で呼び、validate 6 回・render 1 回・画像を 1 回見た。MCP は 0、プラグインは
  このリポジトリのものだけだった。

## テスト

`make check` に入れる（モデルを呼ばない）:

- 機械の採点: スキルの例（side-table・two-tier-shelf）を、その依頼の要件で全項目合格にする。外形・材種・脚の数・棚の
  高さを一つずつ変えた `.nd` は、その項目だけ不合格にする。`.nd` がない作業ディレクトリは「ファイルなし」。
- 依頼ファイル: 10 件すべてが読め、要件の書き方が正しい。
- 記録とレポート: 偽の結果から `report.md` ができ、合格率が行の値から計算し直したものと一致する。時間切れの記録は
  合格率の分母に入らず、件数として出る。
- 回し方: `claude -p` に渡す引数（プラグイン、モデル、MCP なし、道具の制限）を、実際に呼ばずに確かめる。

## 完了条件

- `make check` が通る。最終レビュー（Opus）の指摘を直す。`make ci-local` が通る。
- `--self-check` が通る。
- ★ の 1 件で試運転し、時間と使用量をユーザーに見せる。そのあと `make eval` でベースラインを取り、`report.md` を
  チャットで見せる。普段回す量（頻度）をユーザーと決める。
