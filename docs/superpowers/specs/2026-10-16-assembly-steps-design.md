# 組み立て手順（Assembly Steps）設計

- 日付: 2026-10-16
- ステータス: 下書き（DeepSeek のレビュー前）
- 対象: M4-4（製作支援: どの部材をどの順で、どこに付けるかを読んで組み立てられる）

## 背景

図面（M4-3）には外形と取り付け位置の寸法が入ったが、組み立ての順番はどこにもない。report の「Anchor Details」は部材ごとに
面・辺・オフセットを並べた表で、相手の部材も順番もないので手順としては読めない。また、図面に出せなかった位置（2 段の棚の
下段の棚板 4 枚が幕板のどこに付くか）が残っている（M4-3 で M4-4 に回した）。

## 目的

組み立てる人が、手順ごとの図と数値だけで、どの部材をどの順で、どこに付けるかが分かる。

## 合意した方針（決定事項と理由）

1. **組み立て順は、任意の `steps { }` ブロックにだけ宣言する。接続の行は順不同のまま**（ユーザーの懸念から）。.nd は
   宣言的で、今は書く順が効くのは矛盾した接続の優先だけ。接続を書いた順を手順にする案（A）は、正しい設計でも行の順に意味を
   持たせてしまうので採らない。順番は「組み立て順」という情報として明示的に宣言する。
2. **steps は推奨で、必須ではない**（ユーザー）。小物なら書かなくてよい。書かないときは、部材を 1 本ずつ足す単純な規則で
   手順書を作り、「steps を書くとまとまった手順になる」と案内する。家具の形から部分組みを推測する規則は、机や棚の形を
   前提にした知識になり、形が増えるたびに規則が要るので作らない。
3. **出力は Markdown＋手順ごとの画像**（ユーザーの選択）。エディタや GitHub でそのまま読め、エージェントも読める。
4. **説明の文章は書かない。図と数値（寸法・個数）だけ**（ユーザー: 「テキストで表現しない。数値は OK」）。前後左右の言葉を
   使わないので、家具の正面がどちらかに左右されない。手順の名前は見出しのラベルとしてだけ使う。
5. **画像は立体図 1 枚＋その手順の寸法図**（ユーザーの選択）。立体図は家具の組み立て説明書と同じ見せ方（前の手順までの
   部材は灰色、今回の部材は黒の太線と部材名）。手作りでは穴が開いていないので、今回の部材の位置を寸法で示す正投影図を
   添える（M4-3 の寸法の仕組みを使う）。

## スコープ外

- 留め具・穴の位置の図示（report の Pilot Holes にある）、道具や作業のこつ
- 部材を差し込む向きの矢印、分解図
- 図面と render の「正面」の向き（別件。下の「別件」）

## 設計

### 1. DSL の steps ブロック

```
steps {
  "Left frame":  leg_1, leg_3, apron_upper_left, apron_lower_left
  "Right frame": leg_2, leg_4, apron_upper_right, apron_lower_right
  "Join":        apron_upper_front, apron_upper_back, apron_lower_front, apron_lower_back
  "Shelf":       shelf_1, shelf_2, shelf_3, shelf_4
  "Top":         top_1, top_2, top_3, top_4, top_5, top_6
}
```

- .nd に 0 か 1 つ。どこに書いてもよい。各手順は名前（文字列）と、その手順で付ける部材の ID の並び。
- 名前は見出しのラベル（`Step 1 — Left frame`）にだけ使う。
- 検査（DSL の意味の誤りとして、validate でも出る。何が悪く、どう直すかを書く）:
  - 書き漏れの部材: 「steps leaves out shelf_4; add it to a step」
  - 2 回書いた部材、存在しない部材名（近い名前を候補に出す）、空の手順、steps ブロックが 2 つ
- Python API: `Model.steps: tuple[Step, ...]`（`Step(name: str, pieces: tuple[str, ...])`）。`Model.of(..., steps=...)`。
  検査は `Model` の検証に入れる。

### 2. 手順の計画（どの接続をいつつなぐか）

- 各接続は、その 2 つの部材のうち後の手順で付く部材の手順でつなぐ。
- 手順のあとの組（つないだ接続でつながった部材のまとまり）で、手順の種類を決める:
  - **最初の手順**: 1 つ目。
  - **部分組み（sub-assembly）**: 今回の部材の組に、前の手順の部材が 1 本も入らない（2 つ目以降）。
  - **合わせる（join）**: 今回の部材の組に、手順の前は別々だった 2 つ以上の組の部材が入る。
  - **付ける**: それ以外（前の組 1 つに今回の部材を足す）。
- 描くまとまり: 手順のあと、今回の部材を含む組の部材すべて。
- steps がないとき: 最初に宣言した部材と、それに接する部材のうち宣言順で最初のものを手順 1 にし、以降は「組んだ部材に
  接する部材のうち宣言順で最初のもの」を 1 本ずつ足す。接する部材がなければ、残りのうち宣言順で最初の部材から新しい組を
  始める。部材が 1 本なら手順は 1 つ。
- 計画は build123d に依存しない（`core/assembly/steps.py`）。

### 3. 手順書の中身

`nichiyou-daiku steps shelf.nd` は `shelf-steps/` に `steps.md` と `step-01.png` … を出す（`-o` で場所を変える）。

`steps.md`:

```
# two-tier-shelf: assembly steps

## Step 2 — Right frame (sub-assembly)

![Step 2](step-02.png)

| Piece | Lumber | Length (mm) |
|-------|--------|-------------|
| leg_2 | 2x4    | 781         |
...

| Fastener   | Count |
|------------|-------|
| Dowel 8x30 | 4     |
```

- 見出しの印は `(sub-assembly)` と `(join)` だけ。留め具の名前と数え方は report の買い物リストと同じ。下穴の位置は繰り返さない。
- steps がないときは、冒頭に 1 行「No steps block: one piece per step. Group pieces with a steps block, e.g. ...」を書き、
  CLI も同じ案内を出す（警告ではなく案内）。

### 4. 手順の画像（1 手順 1 枚。左に立体図、右に寸法図）

- **立体図**: +x +y +z から、描くまとまりを描く。前の手順までの部材は灰色の細線、今回の部材は黒の太線、今回の部材には
  部材名を添える（render と同じく、見える中心に重ならないように）。見えない線は描かない。
- **寸法図**: 描くまとまりの正投影図に、今回の部材の位置を M4-3 と同じ描き方（直列寸法・外形・JIS、数字の高さ 2.5mm
  相当、重ならない）で入れる。区切りは今回の部材と、この手順でつなぐ相手の部材の両端。外形は描くまとまりの大きさ。
  図の 2 つの軸の両方に寸法を入れる（区切りがなければ外形だけ）。
- **寸法図の向き**（機械的に決める）:
  1. この手順でつなぐ接続のオフセットが測られる軸（接続の辺の軸）からは見ない（できる限り）。
  2. 残りの軸のうち、今回の部材の投影が互いに重なる面積が最小の軸。同じなら z、y、x の順。
  3. 向きの正負は、今回の部材がほかの部材に隠れる面積が小さい側。同じなら正の側。
- 2 段の棚の例: Step 1（Left frame）は x から見た図で高さ 150・89…・89 と奥行 38・224・38。Step 4（Shelf）は上から見た図で
  脚・棚板 89・隙間 22…（M4-3 で図面に出せなかった位置）。Step 5（Top）は上から見た図で 89 と 13.2 の並び。

### 5. コード

- `dsl/grammar.py`・`dsl/transformer.py`: `steps { }`。`core/model.py`: `Step`、`Model.steps`、検査。
- 新規 `core/assembly/steps.py`（build123d に依存しない）: 手順の計画（部材・つなぐ接続・種類・描くまとまり・留め具の数・
  寸法図の向き）と、steps がないときの順。
- `shell/views.py`: 軸方向 6 つから見る向き。`shell/dimensioning.py`: 部材の一部と任意の向きで区切りを作れるように広げる。
- 新規 `shell/instructions.py`（build123d 必須）: 画像と `steps.md`。寸法の描き方は `drawing.py` から共通に使えるように切り出す。
- CLI `nichiyou-daiku steps FILE [-o DIR] [--size N]`（viz の extra が要る）。
- ドキュメント: DSL 仕様（steps ブロック・steps コマンド）、API 仕様、設計スキル（部材が多い家具は steps を書く）、
  例のファイル（2 段の棚・サイドテーブル・簡単なテーブル）に steps を足す。

## テスト

- 文法と検査（書き漏れ・重複・存在しない名前・空・2 つ）、その文言。
- 2 段の棚の計画: Right frame が部分組み、Join が合わせる手順、各手順でつなぐ接続、描くまとまり、留め具の数。
- steps がないときの順（宣言順、新しい組の始まり、部材 1 本）。
- 寸法図の向きと区切り（棚板の 22 など）、文字と線が重ならない。
- 画像: 今回の部材が黒、前の部材が灰色、見えない線がない、部材名が重ならない。
- CLI: 出すファイル、steps がないときの案内、viz がないときの案内。

## 先に試作で確かめること

新しい部材を黒、前の部材を灰色に分けたまま、見えない線を正しく消せるか。build123d の投影は部材を区別しないので、ここが
いちばんの技術的な不確かさ。2 段の棚の画像を捨て用の試作で作って確かめてから、仕様を確定する。

## 別件

設計スキルの決まり（最初の脚の front 面が家具の正面）では家具の正面は +y を向くが、図面の正面図と render は -y から見ているので、
家具の後ろ側を描いている（左右も逆）。M4-4 の画像は向きを自分で決めるので影響しないが、別に直す。
