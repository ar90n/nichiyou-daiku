# 組み立て手順（Assembly Steps）設計

- 日付: 2026-10-16
- ステータス: 実装済み（DeepSeek のレビュー、試作、Opus の最終レビューを反映）
- 対象: M4-4（製作支援: どの部材をどの順で、どこに付けるかを読んで組み立てられる）

## 背景

図面（M4-3）には外形と取り付け位置の寸法が入ったが、組み立ての順番はどこにもない。report の「Anchor Details」は部材ごとに
面・辺・オフセットを並べた表で、相手の部材も順番もないので手順としては読めない。また、図面に出せなかった位置（2 段の棚の
下段の棚板 4 枚が幕板のどこに付くか）が残っている（M4-3 で M4-4 に回した）。

## 目的

組み立てる人が、手順ごとの図と数値だけで、どの部材をどの順で、どこに付けるかが分かる。

## 合意した方針（決定事項と理由）

1. **組み立て順は、任意の `steps { }` ブロックにだけ宣言する。接続の行は順不同のまま**（ユーザーの懸念から）。.nd は
   宣言的で、今は書く順が効くのは矛盾した接続の優先だけ。接続を書いた順を手順にする案（A）は、正しい設計でも行の順に意味を
   持たせてしまうので採らない。順番は「組み立て順」という情報として明示的に宣言する。
2. **steps は推奨で、必須ではない**（ユーザー）。小物なら書かなくてよい。書かないときは、部材を 1 本ずつ足す単純な規則で
   手順書を作り、「steps を書くとまとまった手順になる」と案内する。家具の形から部分組みを推測する規則は、机や棚の形を
   前提にした知識になり、形が増えるたびに規則が要るので作らない。
3. **出力は Markdown＋手順ごとの画像**（ユーザーの選択）。エディタや GitHub でそのまま読め、エージェントも読める。
4. **説明の文章は書かない。図と数値（寸法・個数）だけ**（ユーザー: 「テキストで表現しない。数値は OK」）。前後左右の言葉を
   使わないので、家具の正面がどちらかに左右されない。手順の名前は見出しのラベルとしてだけ使う。
5. **画像は立体図 1 枚＋その手順の寸法図**（ユーザーの選択）。立体図は家具の組み立て説明書と同じ見せ方（前の手順までの
   部材は灰色、今回の部材は黒の太線と部材名）。手作りでは穴が開いていないので、今回の部材の位置を寸法で示す正投影図を
   添える（M4-3 の寸法の仕組みを使う）。

## スコープ外

- 留め具・穴の位置の図示（report の Pilot Holes にある）、道具や作業のこつ
- 部材を差し込む向きの矢印、分解図
- 図面と render の「正面」の向き（別件。下の「別件」）

## 設計

### 1. DSL の steps ブロック

```
steps {
  "Left frame":  leg_1, leg_3, apron_upper_left, apron_lower_left
  "Right frame": leg_2, leg_4, apron_upper_right, apron_lower_right
  "Join":        apron_upper_front, apron_upper_back, apron_lower_front, apron_lower_back
  "Shelf":       shelf_1, shelf_2, shelf_3, shelf_4
  "Top":         top_1, top_2, top_3, top_4, top_5, top_6
}
```

- 文法: `steps "{" step+ "}"`、`step: ESCAPED_STRING ":" piece_ref ("," piece_ref)*`。`steps` は予約語（部材名・変数名に
  使えない）。手順は 1 つ以上、手順の部材は 1 つ以上（空は文法の誤り）。末尾のカンマは書かない。
- .nd に 0 か 1 つ。どこに書いてもよい。各手順は名前（文字列）と、その手順で付ける部材の ID の並び。
- 名前は見出しのラベル（`Step 1 - Left frame`）にだけ使う。区切りは「 - 」（当初この仕様書は「—」と書いていたが、実装と出力は「 - 」なので仕様書を合わせた）。
- 各手順は必ず新しい部材を含むので、部材を足さずに組同士を合わせるだけの手順は書けない（合わせるのは、両方の組に付く部材を
  足す手順になる）。
- 検査（DSL の意味の誤りとして、validate でも出る。何が悪く、どう直すかを書く）:
  - 書き漏れの部材: 「steps leaves out shelf_4; add it to a step」
  - 2 回書いた部材、存在しない部材名（近い名前を候補に出す）、steps ブロックが 2 つ
  - 手順のあとで、今回の部材が 2 つ以上の組に分かれる手順（「Step 'Join' leaves its pieces in 2 separate parts: split it into
    steps or connect the parts」）。1 枚の図で別々のものを見せないため。組は宣言した接続だけで決まるので、配置を解く前に
    検査できる
- Python API: `Model.steps: tuple[Step, ...]`（`Step(name: str, pieces: tuple[str, ...])`）。`Model.of(..., steps=...)`。
  検査は `Model` の検証に入れる。未知数を解いて `Model` を作り直すところ（`resolve_model`、DSL の変換）でも steps を
  引き継ぐ（引き継がないと、未知数のある設計で steps が黙って消える）。

### 2. 手順の計画（どの接続をいつつなぐか）

- 各接続は、2 つの部材の手順のうち遅いほう（同じ手順ならその手順）でつなぐ。
- **組**: ある手順までに付いた部材だけを、それまでにつないだ接続で結んだまとまり。「手順の前の組」はその手順より前に付いた
  部材だけのまとまり。手順のあと、今回の部材は 1 つの組に入る（2 つに分かれる手順は検査で誤り）。
- 手順の種類（今回の部材を含む組で決める）:
  - **最初の手順**: 1 つ目。
  - **部分組み（sub-assembly）**: その組に、前の手順の部材が 1 本も入らない（2 つ目以降）。
  - **合わせる（join）**: その組に、手順の前の組 2 つ以上の部材が入る。
  - **付ける**: それ以外（手順の前の組 1 つに今回の部材を足す）。
- 描くまとまり: 手順のあと、今回の部材を含む組の部材すべて。部材がつながっていない設計でも、組ごとに描くので図は作れる。
- 留め具の数: `assembly.fasteners` のうち、この手順でつなぐ接続のものを、report の買い物リストと同じ関数で数える
  （配置の矛盾で外された接続の留め具は入らない）。
- steps がないとき（宣言順は部材を宣言した順）: 最初に宣言した部材と、それに接する部材のうち宣言順で最初のものを手順 1 に
  し（1 本だけの手順を作らない）、以降は「組んだ部材に接する部材のうち宣言順で最初のもの」を 1 本ずつ足す。接する部材が
  なければ、残りのうち宣言順で最初の部材と、それに接する最初の部材から新しい組（部分組み）を始める。部材が 1 本なら手順は
  その 1 本の 1 つ。種類の印（sub-assembly / join）も同じ規則で付く。
- 計画は build123d に依存しない（`core/assembly/steps.py`）。

### 3. 手順書の中身

`nichiyou-daiku steps shelf.nd` は `shelf-steps/` に `steps.md` と `step-01.png` … を出す（`-o` で場所を変える）。

`steps.md`:

```
# two-tier-shelf: assembly steps

## Step 2 - Right frame (sub-assembly)

![Step 2](step-02.png)

| Piece | Lumber | Length (mm) |
|-------|--------|-------------|
| leg_2 | 2x4    | 781         |
...

| Fastener   | Count |
|------------|-------|
| Dowel 8x30 | 4     |
```

- 見出しの印は `(sub-assembly)` と `(join)` だけ。留め具の名前と数え方は report の買い物リストと同じ。下穴の位置は繰り返さない。
- 見出しのファイル名: `# <入力ファイル名の stem>: assembly steps`（drawing の表題と同じ）。
- steps がなく手順が 2 つ以上のときは、冒頭に 1 行「No steps block: each step adds one piece. Group pieces with a steps
  block, e.g. ...」を書き、CLI も同じ案内を出す（警告ではなく案内）。手順が 1 つ（部材 1〜2 本の小物）なら、まとめようが
  ないので案内しない（ユーザー:「小物はなくても問題ない」）。

### 4. 手順の画像（1 手順 1 枚。左に立体図、右に寸法図）

- **立体図**: +x +y +z から、描くまとまりを描く。前の手順までの部材は灰色の細線、今回の部材は黒の太線、今回の部材には
  部材名を添える（render と同じく、見える中心に重ならないように。隠れの判定は描くまとまりの部材だけで行う。線の上でも
  読めるよう、部材名の後ろは白で塗る）。前の部材の
  見えない線は描かない。今回の部材の見えない線は黒の破線で描く（ほかの部材に隠れていても、どこに付くか分かる）。
- **部材ごとの隠れ線処理**（試作で確かめた）: 描くまとまりの部材を 1 本ずつ OCCT の `HLRBRep_Algo` に足して一度に
  隠れ線を処理し、`HLRBRep_HLRToShape.VCompound(部材)` などで部材ごとに見える線・見えない線を取り出す。部材同士の
  隠れは正しく消え、灰色と黒に分けられる（build123d の `project_to_viewport` は部材を区別しないので使わない）。
- **寸法図**: 描くまとまりの正投影図に、今回の部材の位置を M4-3 と同じ描き方（直列寸法・外形・JIS、数字の高さ 2.5mm
  相当、重ならない）で入れる。区切りは今回の部材と、この手順でつなぐ相手の部材の両端。外形は描くまとまりの大きさ。
  図の 2 つの軸の両方に寸法を入れる（区切りがなければ外形だけ）。
- **寸法図の向き**（機械的に決める。面積は部材の箱の投影の長方形で測る）:
  1. この手順でつなぐ接続すべての辺の軸（オフセットが 0 や未知数の接続も含む）からは見ない。3 軸とも当たるなら、この
     規則は使わない。
  2. 残りの軸のうち、今回の部材の投影が互いに重なる面積が最小の軸。同じなら、今回の部材の投影の面積が大きい軸。
     それも同じなら z、y、x の順。
  3. 向きの正負は、今回の部材の手前にある描くまとまりのほかの部材が、今回の部材と重なる面積が小さい側。同じなら正の側。
  寸法図でも、今回の部材の見えない線は黒の破線で描く。
- 2 段の棚の例: Step 1（Left frame）は x から見た図で高さ 150・89…・89 と奥行 38・224・38。Step 4（Shelf）は上から見た図で
  脚・棚板 89・隙間 22…（M4-3 で図面に出せなかった位置）。Step 5（Top）は上から見た図で 89 と 13.2 の並び。

### 5. コード

- `dsl/grammar.py`・`dsl/transformer.py`: `steps { }`。`core/model.py`: `Step`、`Model.steps`、検査。
- 新規 `core/assembly/steps.py`（build123d に依存しない）: 手順の計画（部材・つなぐ接続・種類・描くまとまり・留め具の数・
  寸法図の向き）と、steps がないときの順。
- `shell/views.py`: 軸方向 6 つから見る向き。
- `shell/dimensioning.py`: 部材の一部（描くまとまり）を外形にし、選んだ部材（今回の部材とその相手）で区切る直列寸法を、
  任意の向きと軸で作る関数を公開する（今の `chains` もこれで作る）。
- `shell/drawing.py`: 1 つの直列寸法を、置いた図の横に描く関数（今の `_dimension`）を、手順の図からも使える形にする。
  寸法の帯の深さ（`_levels`）と文字の測り方も共通に使う。
- 新規 `shell/instructions.py`（build123d 必須）: 部材ごとの隠れ線処理、手順の画像、`steps.md`。
- CLI `nichiyou-daiku steps FILE [-o DIR] [--size N] [--fillet-radius R]`（viz の extra が要る。プラグインの
  `bin/nichiyou-daiku` も steps を viz の環境で動かす）。画像は 280×140mm の紙を既定 1600px 幅で PNG にする。
- ドキュメント: DSL 仕様（steps ブロック・steps コマンド）、API 仕様、設計スキル（部材が多い家具は steps を書く）、
  例のファイル（2 段の棚・サイドテーブル・簡単なテーブル）に steps を足す。`tests/test_docs.py` は CLI のコマンドがすべて
  DSL 仕様に載っていることと、ドキュメントの `nd` の例と例のファイルがすべて解けて組めることを確かめるので、steps の例は
  ブロックだけの断片ではなく、完全な .nd として載せる。

## テスト

- 文法と検査（書き漏れ・重複・存在しない名前・2 つのブロック・2 つに分かれる手順・予約語）、その文言。
- 未知数のある設計（`simple_table_unknowns.nd` に steps を足したもの）で、解いたあとも steps が残る。
- 2 段の棚の計画: Right frame が部分組み、Join が合わせる手順、各手順でつなぐ接続、描くまとまり、留め具の数。
- steps がないときの順（宣言順、新しい組の始まり、部材 1 本）。
- 寸法図の向きと区切り（棚板の 22 など）、文字と線が重ならない。
- 画像: 今回の部材が黒、前の部材が灰色、前の部材の見えない線がない、今回の部材の見えない線が破線、部材名が重ならない。
- 寸法図の向き: 複数の軸の接続が混ざる手順、3 軸とも当たる手順、今回の部材がほかの部材に隠れる手順。
- CLI: 出すファイル、steps がないときの案内、viz がないときの案内。

## 試作で確かめたこと

部材ごとの隠れ線処理（上の 4）で、2 段の棚の Step 1（Left frame: x から見た寸法図に 150・89・453・89 と 38・224・38）と
Step 4（Shelf: 上から見た寸法図に 89・89・22・89・22・89・22・89・89）の画像が作れた。今回の部材は黒、前の部材は灰色で、
部材同士の隠れも正しかった。試作では部材名の隠れ判定にまだ付いていない部材も入れていて shelf_1 の名前が出なかったので、
本実装では描くまとまりだけで判定する。

## 実装で決めたこと（Opus の最終レビューを受けて）

- 見出しの区切りは `Step 1 - Left frame`（ハイフン）。
- 中心がほかの部材に隠れる今回の部材は、長い辺に沿って 1/4・3/4・1/8・7/8 の点のうち見える点に名前を置く（2 段の棚の
  Step 3 の apron_lower_back、Step 4 の shelf_1 が中心では隠れていた）。どの点も隠れるときだけ名前を省く。
- 同じフォルダに書き直すとき、前の実行で残った手順の画像（`step-NN.png`）は消す。古い画像が今の設計の手順に見えるため。
- `steps` を変数名や接続の部材名に使ったときの文法の誤りには、予約語なので名前を変えるよう添える。
- steps を書くようにという案内は、ページと CLI で同じ文（設計の最初の部材を例に使う）。

## 別件

設計スキルの決まり（最初の脚の front 面が家具の正面）では家具の正面は +y を向くが、図面の正面図と render は -y から見ているので、
家具の後ろ側を描いている（左右も逆）。M4-4 の画像は向きを自分で決めるので影響しないが、別に直す。
